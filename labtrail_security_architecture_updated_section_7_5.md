## Security Architecture & Key Management

### 1. Cryptographic Key Split, Ciphertext Binding & Metadata Scope
Each shared record bundle uses a single-tier direct encryption model (superseding any earlier `SK` / `Wrapped_SK` key-wrapping design):

1. **Key & Share Generation (Client-Side):** For each new share grant or re-encrypted bundle, the sender's browser independently generates a fresh, uniformly random 256-bit `Grant_Key` and a uniformly random 256-bit `Server_Share` using a CSPRNG, then derives the recipient share via bitwise XOR:
   $$\text{Recipient\_Share} = \text{Grant\_Key} \oplus \text{Server\_Share}$$
2. **Authenticated Encryption, Nonce Uniqueness & AAD Binding (Client-Side):** The browser encrypts the record bundle directly under `Grant_Key` using **AES-256-GCM** with a 96-bit random nonce (`IV`). A nonce must never be reused with the same `Grant_Key`; generating a fresh `Grant_Key` and a fresh random 96-bit nonce for every new encryption operation enforces this rule. Because AES-GCM Additional Authenticated Data (AAD) is authenticated in plaintext rather than encrypted, AAD contains **only** public, non-sensitive canonical fields—specifically `grant_id` and `schema_version`—never patient data or share scope details. Encryption outputs `Ciphertext` (including the 128-bit authentication tag).
3. **Storage & Metadata Minimization:** `Recipient_Share` is never sent to the backend and is placed exclusively in the URL fragment (`#<Recipient_Share>`) of the share link. The backend stores only `Server_Share`, `Ciphertext`, the nonce, `schema_version`, and minimal operational metadata required for authorization, lifecycle state, and expiry (such as `grant_id`, authorized clinician identifier, creation/expiration timestamps, and revocation status). Server-side metadata never contains patient clinical data, record contents, or detailed share scope.
4. **Client-Side Reassembly & Authenticated Decryption:** When an authorized clinician opens the share link, the gateway verifies clinician authentication and second-factor authentication (2FA) before authorizing the release of `Server_Share` and `Ciphertext`. The browser reads `Recipient_Share` locally from `window.location.hash`, reconstructs $\text{Grant\_Key} = \text{Server\_Share} \oplus \text{Recipient\_Share}$ in memory, and independently constructs the expected AAD from the requested `grant_id` and expected `schema_version` (rather than relying on server-supplied AAD values) before verifying the GCM authentication tag and decrypting `Ciphertext`. In implementation, the browser must release or render zero plaintext unless GCM authentication succeeds. This detects ciphertext substitution across grants or protocol versions, though it does not prevent replay of valid ciphertext within the same grant. The complete `Grant_Key` is never transmitted to or persisted on the server.

> **Implementation Note:** All references to a separate content-encryption key (`SK`) and wrapped key (`Wrapped_SK`) are deprecated and removed from the upload, storage, and viewer specifications.

---

### 2. Trust Boundary & Hosting Operator Scope
Under a **trusted-client assumption**—meaning the clinician's browser executes authentic, unmodified client code—the server and hosting operator cannot reconstruct `Grant_Key` or decrypt patient records from server-held materials (`Server_Share` and `Ciphertext`) alone, as an independent, uniformly random `Server_Share` reveals zero information about `Grant_Key` without `Recipient_Share`.

Because the web application bundle (JavaScript/WebAssembly) is delivered by the hosting infrastructure, zero-access confidentiality at rest depends on the integrity of the served client code rather than cryptographic isolation from a malicious or compromised application host.

---

### 3. Link & URL Fragment Exposure Scope
Placing `Recipient_Share` in the URL fragment (`#`) prevents it from being transmitted in standard HTTP request headers or logged by backend web servers. However, because the fragment travels inside the share URL itself, it is **HTTP-request isolated** rather than delivered out-of-band:

- Any system or script with access to the full URL—including email clients, messaging archives, browser history, or scripts executing within the page origin—can read `Recipient_Share`.
- Possession of the full URL alone is insufficient to decrypt records; retrieving `Server_Share` from the gateway still requires valid clinician authentication and 2FA to authorize release.
- Deployments requiring strict out-of-band channel separation must transmit `Recipient_Share` over a channel independent of the link URL (e.g., separate SMS or verbal PIN).

---

### 4. Access Revocation, Freshness Verification & Post-Retrieval Limitations
**Revocation Propagation & Freshness Enforcement (Operational Requirement)**
As an operational availability and access-control requirement (rather than a cryptographic guarantee), the **5-second** revocation clock starts when LabTrail accepts a revoke request and commits the revocation state. Within 5 seconds of accepting the request, the backend deletes `Server_Share`, persists a revocation tombstone across primary datastores, read replicas, and edge/API caches, and ensures every gateway denies access. At expiry, every gateway denies access at `expires_at`; deletion of `Server_Share` and tombstone propagation must complete within 5 seconds after that time. Neither propagation window is an access grace period:
- **Authoritative Status & Bounded Leases:** A cached "active" status is never sufficient on its own to authorize release. Before releasing `Server_Share` or `Ciphertext`, a gateway must verify current grant status via either (a) a strongly consistent authoritative read against the primary grant/revocation store, or (b) a strictly bounded, revocable lease whose maximum TTL plus worst-case clock skew is strictly less than the 5-second revocation bound (e.g., $\le 2\text{ seconds}$), combined with active cache invalidation.
- **Expiry Enforcement:** Before every release, the gateway checks against authoritative server time that the grant is active and `now < expires_at`. A lease must expire no later than the grant's `expires_at`; delayed expiry cleanup or tombstone propagation never extends access.
- **Gateway Enforcement:** Blocks all subsequent gateway requests for `Server_Share` and `Ciphertext`, invalidates active server-side viewer sessions, and emits a **best-effort** close/purge signal to active browser viewers.
- **Backup Hygiene:** Prevents backup restores from re-exposing `Server_Share` (either by excluding `Server_Share` from restorable snapshots or enforcing the revocation tombstone prior to any gateway read).
- **Fail-Closed Behavior:** During network partitions, primary datastore unavailability, expired leases, or any state of uncertain freshness where a gateway cannot positively confirm the grant is currently active, the gateway must fail closed and deny access.

> **Verification Requirement:** Because the 5-second deletion-and-propagation target is an operational control, it must be demonstrated and continuously verified through automated integration and fault-injection tests covering primary stores, read replicas, **stale-positive caches** (delayed or dropped invalidation events), **network partitions and datastore failures**, and backup-restoration workflows.

**Post-Retrieval Limitations**
Revocation is a forward-looking server control; it cannot force a client browser to close, enforce client-side erasure, or retroactively revoke materials already delivered. Once a clinician's browser has retrieved `Server_Share` and `Ciphertext` alongside `Recipient_Share`, the server cannot prevent a recipient or local script from retaining, replaying, or decrypting local copies of the ciphertext, key shares, or decrypted files offline, nor can it prevent screen capture of rendered records.

### 5. Patient / User-Facing Consent & Sharing Disclosure
> **Before you share this link:**
> Your records are encrypted in your browser before upload, and LabTrail servers never hold the complete key needed to decrypt them. Accessing your records requires **both** the full share link (which contains the recipient key share) **and** a verified clinician login with two-factor authentication (which authorizes our server to release the second key share).
>
> **What revoking access does—and does not—do:**
> You can revoke a link at any time: within 5 seconds after LabTrail accepts the revocation request, further server access is blocked and a best-effort close signal is sent to open viewers (if your device is offline or the request fails, revocation has not yet taken effect). However, revoking access cannot force a recipient's browser to close, nor can it delete copies of your records, encrypted files, or key material that a recipient has already downloaded, saved, or captured on their device before revocation. Only share links with trusted clinicians over secure channels, as anyone who obtains the full URL holds one of the two shares needed to decrypt your records.

### 7.5 Cryptographic Design & Key Management

To substantiate constraint **C-08 (Custody Model)**—which mandates that the hosted service (Zone 2) operate as a content-blind storage provider—LabTrail combines client-side local record encryption in Zone 1 with a single-tier, 2-of-2 XOR key-split and client-side reassembly protocol for recipient grants across Zones 2 and 3. *(Note: This single-tier direct encryption model supersedes all earlier `SK` / `Wrapped_SK` / `SK_Frag` key-wrapping designs.)*

#### 1. Local Record Key Generation & Management (Patient's Device — Zone 1)
* **Master Key Generation (`MK`):** During initial account setup, a client-side Cryptographically Secure Pseudo-Random Number Generator (CSPRNG) generates a random 256-bit Master Key (`MK`).
* **Data Encryption Key (`DEK`):** The client generates a random 256-bit Data Encryption Key (`DEK`) for AES-256-GCM encryption of local source documents, candidate extractions, and verified records in Zone 1 (NFR-03). The `MK` wraps the `DEK` using AES-256-GCM with a fresh nonce and purpose-specific AAD; the wrapped `DEK` is stored locally.
* **Passphrase Unlock:** The patient's passphrase and a unique random client-side salt are processed through Argon2id to derive a Key Encryption Key (`KEK`). The `KEK` wraps the `MK` using AES-256-GCM with a fresh nonce and purpose-specific AAD. The wrapped `MK`, salt, nonce, and KDF parameters are stored locally; the passphrase and plaintext keys are not sent to the server.
* **Recovery Phrase:** At setup, the client generates a high-entropy recovery phrase and displays it to the patient. A separate Argon2id-derived recovery key, using its own random salt, wraps the `MK` with AES-256-GCM and a fresh nonce. The patient must save the phrase; it is not recoverable by LabTrail, and LabTrail holds no plaintext key or recovery phrase (FR-24, DR-02). The passphrase or the recovery phrase can unlock the `MK`, which unwraps the `DEK`. Optional platform-synced key storage must not expose plaintext keys to LabTrail; no operator escrow is permitted.
* **Key Residency:** Plaintext `MK` and `DEK` remain in Zone 1 device memory and are cleared from application-managed buffers on lock or session end on a best-effort basis.
